# @ryharness/schedule

提醒：到点了，在原来的会话里说一句。

上游 dsh 把这一族拆成两个包（schedule 持久化与调度、tool-schedule 模型工具）。这轮把两者的语义合在一个包里。

## 提供什么

- `ScheduleService` —— 建提醒、算下一次响、到点投递、停用 / 启用 / 删除。
- `ScheduleStore` —— 存储接口；包内给 `FileScheduleStore`（落盘，跨 Host 重启存活）与 `MemoryScheduleStore`。
- 五种触发方式 —— 一次性 / 固定间隔 / 每日 / 每周 / cron，各有自己的时间计算。
- 自己写的 cron 解析器 —— `parseCron()`，五段（分 时 日 月 周），**不引外部依赖**。
- 四件模型工具 —— `schedule_create` / `schedule_list` / `schedule_update` / `schedule_delete`。

## 到点时怎么投

提醒到点时，作为一条**普通的后续消息**投进原会话——不是邮件、不是短信、不是系统推送。

投递由宿主给一个回调，本包**不碰会话存储**：

```ts
const service = new ScheduleService({
  storePath: join(dataDir, 'schedule.json'),
  deliver: (scheduleId, conversationId, text) => {
    // 宿主把 text 写进 conversationId 这个会话，并推给界面
  },
})
```

`deliver` 的签名就是上游那一档：**`deliver(scheduleId, conversationId, text)`**。

## 五种触发方式

| 方式 | 怎么写 | 下一次什么时候响 |
|---|---|---|
| 一次性 | `{ kind: 'once', at }` | 那个时刻；响过就没有下一次 |
| 固定间隔 | `{ kind: 'interval', everyMs }` | 对齐到建立时刻的每个整间隔 |
| 每日 | `{ kind: 'daily', time: '09:00' }` | 每天那个钟点（本地时间） |
| 每周 | `{ kind: 'weekly', weekday: 3, time: '08:00' }` | 每周那天的那个钟点 |
| cron | `{ kind: 'cron', expression: '0 9 * * 1-5' }` | 按表达式（本地时间） |

两处时间基准要分清：

- **钟点类**（每日 / 每周 / cron）按**本地时间**算——「每天 9 点」就是每天早上九点。
- **间隔类**按**建立时刻对齐**算——每 30 分钟一次就是建立后的每个整半小时，**不会因为某一次投递晚了就整体漂移**。

## 一次性与重复触发

这两件事的语义不同，包里也是分开处理的：

- **一次性**响完状态转 `completed`，**没有下一次**（`nextRunAt` 消失）。再 tick 也不会响第二遍。
- **重复触发**（间隔 / 每日 / 每周 / cron）每次响完重新排下一次，状态留在 `active`。

## cron 解析器

自己写的五段解析器，零外部依赖。支持：

| 写法 | 意思 |
|---|---|
| `*` | 全段 |
| `*/n` | 从最小值开始每隔 n（`*/15` = 0,15,30,45） |
| `a` | 单个值 |
| `a-b` | 闭区间 |
| `a-b/n` | 闭区间里每隔 n |
| `a/n` | 从 a 到最大值每隔 n |
| `1,15,20-30` | 上面这些拼起来的列表 |

语义按标准 cron：**日**与**周**同时被限定时（都不是星号），任一匹配就算那天命中（传统 cron 的 OR 规则）。

星期写 `7` 也认（归一成周日）。越界的值、不是数字的字段、不合法的步长、反着的范围，一律报错并说清范围。

往后五年内一次都不命中的表达式（比如「2 月 30 日」）不会死循环——`nextCronTime()` 返回 `undefined`。

## 跨重启与错过的时间

提醒落盘，跨 Host 重启存活。进程停着的时候到了点，重启后按策略处理：

| 策略 | 干什么 |
|---|---|
| `skip`（缺省） | 跳过错过的那些次，直接排到下一次 |
| `catch-up` | 把错过的那次补上（**只补一条**，不补一堆） |

策略在服务构造时定：`new ScheduleService({ missedPolicy: 'catch-up' })`。当前策略可以问 `service.policy`。

`catch-up` 补的那次会在下一次 `tick()` 时投出去——所以宿主启动后记得 tick 一次。

## 停用、启用、删除

- **停用**（`disable`）：留着，但不再响，也不再排下一次。
- **启用**（`enable`）：重新排下一次。
- **删除**（`remove`）：**要确认**。不可逆的操作不许「手一滑就没了」，所以 `remove(id, confirmed)` 在 `confirmed` 不是 `true` 时抛 `CONFIRMATION_REQUIRED`——宿主拿到这个码就知道该弹确认框。模型工具那一层对应的是 `schedule_delete` 的 `confirmed` 参数。

## 归属按会话

提醒归会话所有：别的会话的提醒既不该被看见，也不该被改掉或删掉。

- `service.list(conversationId)` —— 按会话列。
- `service.listAll()` —— 宿主视角的全部清单（任务管理页看的就是它），含已停用的。
- 模型工具那一层还会再核一遍归属：拿着别的会话的提醒 id 去改，直接拒绝。

## 模型侧的四件工具

- **`schedule_create`** —— 参数 `text`（到点时讲什么）、`kind`（什么时候响）、以及 `at` / `every_minutes` / `time` / `weekday` / `cron` 里对得上的那几个。
- **`schedule_list`** —— 列出当前会话的提醒（内容、什么时候响、启用还是停用、响过几次）。
- **`schedule_update`** —— 改内容、换触发方式、停用 / 启用。
- **`schedule_delete`** —— 删一条，必须带 `confirmed: true`。

用户只是要「先别提醒了」时用 `schedule_update` 把 `enabled` 设成 `false`，别删——停了还能再开，删了就没了。

## 不做什么

- **不做跨会话的共享提醒**。提醒归会话所有，一个会话的提醒不会投到另一个会话。
- **不做任务管理页**。这一族给的是服务与工具；界面上的待办与已停用任务列表由宿主做（用 `listAll()`）。
- **不做时区**。所有钟点按宿主所在时区算，没有「按某个时区」的选项。
- **不做投递重试**。投递失败（宿主挂了、会话没了）就当这次没送到，提醒照旧排下一次。
- **不做提醒的模板、标签、分类**。一条提醒就是「说什么 + 什么时候响」。

## 与上游 dsh 的差距

- **独立的调度进程**：上游的 schedule 由 Host 拥有一个调度器来驱动。这轮驱动方式是宿主自己按周期调 `service.tick()`（服务端插件里已经接了一个定时器）。
- **跨会话的任务管理页**：上游有专门的页面，能不打开原会话看待办与已停用的任务并确认删除。这轮给了服务能力（`listAll()` + `remove(id, confirmed)` 的确认口径），页面本身由宿主做。
- **投递历史（delivery history）**：上游记着每次投递的回执与历史，供人回看。这轮只记 `fireCount` 与 `lastRunAt`，没有完整的投递历史。
- **时区**：上游有显式的时区处理（见上游那条「explicit schedule time zone」的改动）。这轮一律按本地时区算。
- **上游的 preset 作用域**：上游的 model 工具按 preset 作用域裁剪（每个助理能看到哪些提醒）。这轮按会话归属裁剪。
- **上游的 cron 表达式更宽**：上游的 cron 解析器支持更多写法。这轮只支持上表那几档（够覆盖「工作日早上九点」这类真实需求），秒段、`@daily` 之类的别名、`L`/`W`/`#` 这些都没有。
