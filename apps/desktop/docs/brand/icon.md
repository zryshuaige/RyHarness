# 应用图标：橘猫

## 这是什么

RyHarness 的应用程序图标是一只**橘猫**：大眼、微笑、两只前爪搭在底板边缘，坐在一块琥珀色
圆角方形底板上。它与应用界面的暖琥珀 / 奶油 / 深棕调性同源——底板的琥珀色就是界面里
`--accent` 那一档暖色。

全应用只有**一只猫**，出现在这些地方，全部由同一份资产导出：

| 位置 | 资产 | 档位 |
| --- | --- | --- |
| 母版（唯一真源） | `assets/brand/mark.png` | 953×953 |
| 应用图标 | `assets/icon-{16,24,32,48,64,128,256,512,1024}.png` | 逐档独立导出 |
| Windows 图标（exe 内嵌 + 开始菜单快捷方式） | `assets/icon.ico` | 16/24/32/48/64/256 |
| 任务栏 / 窗口 | `assets/icon.ico`，打包后从 `resources/icon.ico` 读（asar 之外） | 16/24/32/48/64/256 |
| 托盘 | `assets/icon-16.png`（HiDPI 屏 `icon-24.png`） | 16 / 24 |
| 网页端标签页 | `assets/favicon-{32,128}.png` → `renderer/public/` | 32 / 128 |
| 应用内徽标 `<Cat>` | `assets/cat.png` → `renderer/public/cat.png` | 256 |
| 启动屏 | `/app/cat.png`（index.html 内联引用） | 256 |

## 母版

`assets/brand/mark.png`，953×953、RGBA、四角抠成圆角方形。项目自有资产，随本项目以 MIT
许可分发，素材来源与授权见仓库根 `NOTICE.md`。

母版是从 1024×1024 的原始素材**制备**出来的，制备参数记在这里以便复现（这是一次性动作，
`gen-icon.mjs` 不做这一步——母版本身就是入库的源资产）：

| 步骤 | 参数 | 为什么 |
| --- | --- | --- |
| 裁到琥珀底板本体 | 原图 `extract({ left: 35, top: 30, width: 953, height: 953 })` | 原图四周有一圈白边（上 29 / 下 40 / 左 33 / 右 35），底板外沿实测在 x∈[35, 987]、y∈[30, 982] |
| 抠圆角 | 圆角半径 = 边长 × 0.245 | 原图是白底不透明，四角不抠会在深色任务栏上留下一圈白角 |
| 重编码 | `png({ compressionLevel: 9, effort: 10 })` | 1.83 MB → 345 KB。sharp 的 PNG 输出带调色板量化：母版因此是 253 色的索引 PNG（带 `tRNS` 透明块），逐像素平均误差约 1/255（同一张原图在 956 裁切版本上实测 mean 1.12 / max 34），1:1 查看无可见色阶断层 |

母版被 `gen-icon.mjs` 校验（边长必须是 953、必须带 alpha），换错了当场失败而不是产出一批
带白角的图标。

母版上几处后面反复要引用的实测坐标：

| 量 | 实测值 |
| --- | --- |
| 自带圆角半径 | 沿对角线第一个不透明像素在 68px，圆角半径 = 68 ÷ (1−1/√2) ≈ 232 ≈ **0.245 × 953** |
| 左耳尖 | 约 **(234, 125)** |
| 右耳尖 | 约 **(708, 70)**（猫头是歪的，右耳比左耳高 55px） |
| 耳尖横向跨度 | **474px** |

## 逐档策略：九档都是整幅 + 同一个圆角

每档都是**独立从母版缩放**，不是从 1024 或从 256 降采样。降采样只会把上一档的结果再缩小
一遍：母版的缩放核一旦在小尺寸上把五官糊掉，后面的降采样拿不回细节。

| 档位 | 策略 | 依据 |
| --- | --- | --- |
| 全部九档 | **整幅母版 + 同一个 0.245 圆角遮罩** | 见下面两节：裁窗与圆角在几何上互斥 |

### 为什么取消「脸部特写」裁窗

早期 24/32/48 三档裁到脸、且**不扣**圆角（满出血直角方块），其余档整幅加圆角。结果同一枚
托盘图标在非 HiDPI 屏下是圆角、HiDPI 屏下是直角；`favicon-32` 在 32px 下是硬方块、
`favicon-128` 缩到 32px 是圆角——同一枚图标两种视觉身份。

统一外轮廓只有两条路，实测都指向「取消裁窗」：

1. **给裁脸档也扣同一个圆角 → 必然削耳。** 半径 `0.245·S` 的圆角只保住裁窗顶边**中间
   51% 宽**的像素（`x ∈ [x0+0.245S, x0+0.755S]`）。母版上两只耳尖横向跨度 474px，要让它们
   都落进安全带需要 `474 ≤ 0.51·S`，即 **S ≥ 929**；母版边长只有 953，窗还得再让出耳尖的
   纵向余量（耳尖在 y≈70~125，窗顶还得再往上）。也就是说「裁脸 + 圆角」不是风格取舍，是
   几何上做不到。旧的 700 窗（`{x:128, y:80, size:700}`）实测右耳尖在 y≈70，**在窗外
   10px**——这正是评审截图里那道硬直切口。
2. **一律不扣圆角 → 整幅档丢掉底板的圆角轮廓。** 母版本身就是抠好的圆角底板，Windows 任务栏
   / 托盘与标签页 favicon 都是圆角更可识别，退成硬方块是把品牌资产做差。

所以九档（含 `favicon-32`）一律整幅 + 同一个圆角。托盘的 16 档与 HiDPI 24 档从此是同一枚图
的两次缩放，不再是两种零件。

`plateMask` 仍然保留：它把每档的圆角**归一到同一个半径**，母版自带的圆角与它在角弧的抗锯齿
上略有出入（实测合成后 3,632,836 个像素里有 140,597 个变化，最大 Δ 113，全部落在角弧上），
保留它等于把「轮廓随尺寸不变」变成代码里可读的一条规则，而不是依赖母版制备时的巧合。

### 16px 到底糊不糊（实测复核）

原文写「裁到脸反而糊成一团（实测 420/500/600 三档在 16px 全糊）」。逐条复现后**这个说法不
成立**：母版 → 各裁窗 → 16px lanczos3，数亮度 < 0.25 的深色像素（眼与鼻）与粉鼻像素：

| 16px 候选裁窗 | 深色像素 | 粉鼻像素 | 耳朵 |
| --- | --- | --- | --- |
| 整幅（现用） | **9** | 23 | 完整 |
| face700 `{128,80,700}` | 8 | 25 | **右耳尖切掉 10px** |
| face600 `{178,130,600}` | 15 | 20 | **两只耳尖都在窗外** |
| face500 `{228,180,500}` | 21 | 13 | **两只耳尖都在窗外** |
| face420 `{268,220,420}` | 30 | 13 | **两只耳尖都在窗外，且眼已贴边** |

（上面是不带圆角遮罩的裸对比，所以整幅是 9；实际产物带遮罩后是 5/27。）

四档放大后都能数出两只深色眼 + 粉鼻，**没有哪一档是「糊成一团」**。深色像素从 9 涨到 30 也
不是「更清晰」，而是脸被放大到耳尖之外——窗里只剩一张脸，已经不是那只猫了。真正不糊的是
整幅：它在 16px 上仍然是「琥珀底板 + 两只耳朵 + 两眼 + 粉鼻」。

所以 16px 保持整幅，不是因为它最清晰（它确实不是深色像素最多的那一档），而是因为**其余
几档要靠切耳朵来换清晰度**，而统一外轮廓这条硬约束本来就要求整幅。带遮罩的实测档位数据：

| 档位 | 深色像素 | 粉鼻像素 | 顶部 30% 条带内耳廓奶油色像素（左/右） |
| --- | --- | --- | --- |
| 16 | 5 | 27 | 1 / 3 |
| 24 | 13 | 39 | 4 / 9 |
| 32 | 22 | 71 | 11 / 20 |
| 48 | 62 | 187 | 28 / 47 |
| 64 | 124 | 290 | 55 / 78 |
| 128 | 555 | 1213 | 233 / 316 |

「耳朵完整」因此被写成了可断言的不变量（`brand-tiers.test.ts`）：每档顶部 30% 条带里左右
两侧都数得到耳廓的奶油色（`r−b < 70`，底板橙是 130~190）。旧的断言只验「有深色像素」，
切掉一只耳朵照样过——这是门禁的结构性盲区。

## 重新生成

```bash
node apps/desktop/scripts/gen-icon.mjs        # 或 pnpm --filter @ryharness/desktop gen:icon
```

脚本**完全离线**，只读 `assets/brand/mark.png` 与本仓库内的其它文件，不发任何网络请求。产物：

- `assets/icon-{16,24,32,48,64,128,256,512,1024}.png`
- `assets/icon.ico`
- `assets/favicon-{32,128}.png`、`assets/cat.png`
- `assets/brand/tiers.json`（档位表 / 圆角半径 / 接线文件名——主进程与测试读的是同一份契约）
- `renderer/public/{cat.png,favicon-32.png,favicon-128.png}`（vite 原样拷进 dist 根目录）

## 任务栏那枚图标为什么从 asar 外面读

任务栏按钮的图标取自窗口的 WM_SETICON；取不到才继续往下退到 exe 内嵌图标，而这一退在
Windows 11 上会被显式 AUMID 截断——进程带着 AUMID 时 Explorer 先找该 AUMID 注册的资源，
找不到就不再退到 exe，直接画默认字形。所以 WM_SETICON 必须真的设上。

窗口图标因此喂多档 `icon.ico` 而不是单张 256 档 PNG（Electron 自己的 `BrowserWindow.icon`
文档也写着 Windows 上推荐 `ICO`），并且打包后从 `resources/icon.ico` 读——这个路径是由
Chromium 的图片加载器读的（不是 Node 的 `fs`），要穿过 `app.asar` 归档，而那一环是整条图标
链上唯一只在开发态（真实文件）验过的。托盘两档仍取 asar 内的 PNG：它们走的是
`nativeImage`，与窗口图标不是同一条路。

`apps/desktop/tests/win-taskbar-icon.test.ts` 把这四段（ico 档位、打包态路径落在 asar 外、
`extraResources` 真的把文件放到那个位置、`win.icon` 与窗口图标同源）逐条钉住。

## 为什么没有 .svg 图标

母版是**位图**，产不出真矢量。此前的几何 SVG 母版（`assets/brand/cat-face*.svg` 三态）
连同「内嵌 base64 位图的假矢量」包装法一起作废了：与其给浏览器一个自称矢量、实际仍是
PNG 的文件，不如直接给 PNG。消费方也都不需要 `.svg`——安装包取 `icon.ico`，
Chromium（桌面应用唯一的渲染引擎）直接支持 PNG favicon。

三态（idle / thinking / happy）随之作废：位图没有可换的眼形与嘴形。应用内「正在思考」
改由 `components/TypingDots.tsx` 的打字动画表达。
